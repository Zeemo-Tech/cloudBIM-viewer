# V5 分类去噪：第二轮性能排查

本轮以工作区已有的性能修复为基线，保留原有修改；不降低采样精度、邻居数或几何判定阈值。测试使用项目 Python 3.11 虚拟环境，完整基准直接调用算法用于排除服务和网络等待，没有启动独立开发服务，也不更新资产 latest。

## 原因与修复

1. 掩码的源索引映射在当前内部调用链中正确，但每次查询都调用 `np.unique(axis=0)` 对整数格点做结构化记录排序，并为每个格点重新扫描整个 inverse 数组。百万点、千格点的基线读取/写入分别约 0.73/0.73 秒。
2. 同样的结构化记录排序反复出现在连通分组、台面/夹具占用格点、多尺度特征抽样和显示标签分组中。真实 281,507 点上，仅排序耗时约 96 毫秒，列式稳定整数排序约 9 毫秒。
3. 去噪对每个点计算协方差特征值，但该结果只影响“邻居少且物理范围紧凑”的小组件判定。密集点不可能满足此前置条件。
4. 基础 PCA 临时文件先压缩，后续反复解压，导出时再压缩一次。阶段性改为不压缩后，真实 141,753 点分块的一次写入从 0.397 秒降到 0.0068 秒；读取从 0.046 秒降到 0.0080 秒。随后按用户提出的 16 GiB 以上环境要求，进一步改为下述共享内存方案；不压缩文件只保留为预算不足时的回退。

新增 `algorithms/spatial_keys.py`，按整数列做稳定字典序排序，一次生成分组边界。与原实现保持相同的格点顺序、首次源点选择、inverse 映射、组件内部源点顺序。没有使用浮点键或可能溢出的混合进制编码，覆盖有符号/无符号 64 位极值。

该工具限定输入为至少一列坐标的二维整数格点数组，明确拒绝浮点和零列数组；不声明支持 NumPy `unique` 的其他输入域。

掩码和显示标签直接遍历连续分组，移除每格点一次的全量扫描；协方差仅在可能满足紧凑小组件条件的行上计算。局部噪声密度证据及全部最终分类条件保留。

线程调度也做了单变量对照：真实夹具点块使用原有 4 线程比强制 1/2 线程快，因此保留现有查询并行策略。

## 验证方式

- `test_rebar_integer_keys.py` 对照 NumPy 的唯一格点、首次索引和 inverse，覆盖空输入、重复格点、负值、64 位边界及稳定分组，并阻止密集连通分组退回结构化排序。
- `test_rebar_v5_denoise_performance.py` 用 10,000 个密集点加噪声组件验证分类，并将协方差拟合从 10,005 行约束到最多 5 行；修复前该断言失败。
- `test_rebar_v5_scratch_io.py` 验证基础特征临时文件不再执行 Deflate，数组及源索引保持一致；原实现下该断言失败。
- 保存本轮修改前源码，在真实点块上比较连通分组、夹具面、多尺度特征、噪声及疑似噪声数组。
- 完整基准使用同一 9,216,369 点 LAS 和真实 PNTS 瓦片，独立输出版本，再逐数组和逐瓦片比较前一完整产物。

## 共享内存与逐点属性列

- `ChunkCache` 用同一份 NumPy 列数组保存基础特征、稀疏边界更新和原始标签。命中时直接共享数组，不重新压缩、读取或复制整块数据。预算不足时按 LRU 写出，重新读取后恢复缓存；最终产物按原格式持久化和压缩。
- 导出后 Runtime 继续使用内存中的标签列，不切换到刚写出的压缩文件再读取。
- 显示邻域 KD-tree 和对应标签列使用独立、有预算的 LRU，跨瓦片共享。归属重新确认会使这些索引失效，防止使用旧标签。
- 边界 PCA 仍遵守台面排除、夹具排除的先后顺序。邻域改变时重新计算必要的边界特征；已计算的稀疏更新在后续归属处理中复用。
- 缓存默认上限由 `REBAR_MEMORY_CACHE_MB=4096` 设置，容器和主机可用内存取较小值，先预留 2 GiB，再最多使用剩余可用内存的一半。预算的 7/8 用于列数组，1/8 用于显示索引。`0` 表示完全采用磁盘回退。此值是缓存预算，不是整个进程的 RSS 上限。
- 空间索引仍采用分块 memmap；这是原始数据的随机访问索引，由操作系统缓存文件页，不反复进行 NPZ 压缩/解压。
- V5 全量标签已经是与 `source_index:uint64` 对齐的属性列，包括 `scene_class`、`rebar_class`、`rebar_instance`、`rebar_direction`、`rebar_flags`、置信度、夹具种类和钢筋角色。显示 PNTS 已有对应的二进制逐点属性，前端直接将其装入几何属性列。原始 LAS 保持不变，全量属性按源记录索引保存到衍生产物。
- 当前显示瓦片没有精确源记录索引；显示点可能被抽稀/量化，因此继续从原始标签邻域传递并保留歧义。需要精确复用原始标签时应使用全量 `source_index` 属性列，不能把显示点近邻当作原始点身份。

缓存集成后首轮 257 项回归测试通过，补充嵌套进程组预算用例后，最终 **258 项回归全部通过（51.85 秒）**。额外对照在 27,074 点物理场景上分别运行纯磁盘/内存模式，22,005 个基础特征、更新、标签及显示数组逐个精确相等，实例、连接、层、交点与几何模型相同。内存模式中间分块 `diskReads=0`、`diskWrites=0`；重复显示查询有 674 次索引命中。结果见 `memory-equivalence.json`，这些计数属于该合成场景，不是 921 万点实测。

新增测试覆盖 LRU 淘汰、零预算、超大分块、整数标签回读、覆盖旧值、索引失效、容器内存限制与资源清理。额外修复了诊断字段引用活动缓存统计会在清理后改变返回 manifest 的问题；返回响应与磁盘 manifest 相等的回归已通过。

## 重启核查与实测限制

用户报告的 00:13 重启发生前，大容量内存缓存尚未实现。系统日志显示 00:13:36 `systemd-logind` 宣布重启，00:13:41 有序同步文件系统并结束进程。未发现重启前的 Linux OOM 杀进程或内核崩溃记录；更早存在 NVIDIA 分配失败日志，但不能据此归因本次重启。现有证据不能确定重启请求的发起者，也不支持将其直接归因于本次分类算法耗尽内存。

最终内存版冷基准使用独立 systemd scope，设置 `MemoryMax=8G`、`MemorySwapMax=0`，每 5 秒记录该组内存与主机可用内存。基准 RSS 目标根据用户明确提出的 16 GiB 环境调整为 8 GiB，时限仍为 900 秒；默认缓存上限为 4 GiB，还会按该组可用内存进一步缩小。
