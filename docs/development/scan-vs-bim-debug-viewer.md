# Scan-vs-BIM 逐根调试

第三步右侧的“Scan-vs-BIM 调试 → 独立端口调试”打开 **5174** 的调试前端，复用第三步查看器与现有 8090 后端。5173 主界面保留运行；两套前端使用不同进程和 Vite 缓存。调试前端在第三步默认进入隔离模式，也可在主界面点击“逐根调试”。

可将现有 `/alignment?...&step=3` 地址的端口改为 5174 并追加 `&debug=rebar`；`debugBar=<IFC GlobalId>` 可指定钢筋。“独立端口调试”保留主机名、项目、资产和当前钢筋参数。独立浏览器来源可能要求使用现有账号登录；沿用原认证流程。

```bash
scripts/cloudbim-dev.sh debug-start  # 要求主栈已经运行；固定 5174，冲突时报错
scripts/cloudbim-dev.sh status
scripts/cloudbim-dev.sh debug-stop  # 只停止调试前端
```

`scripts/cloudbim-dev.sh stop` 也会停止调试前端。进程号与日志分别位于 `.cloudbim/rebar-debug.pid`、`.cloudbim/rebar-debug.log`。独立配置 `vite.rebar-debug.config.ts` 继承主配置的代理和插件，启用严格端口检查，不自动换端口。此独立进程是用户明确要求的调试服务，由项目管理脚本启动。

## 操作

- 有有效结果时默认显示偏差着色并隐藏扫描点，避免密集点遮住结果表面；重新计算成功后同样切回此模式。没有结果时临时显示原设计，结果就绪后恢复着色意图。
- 顶部“偏差着色”按钮直接切到结果并隐藏扫描点，“设计 + 钢筋簇”切回原设计与扫描的隔离对照；仍可单独打开“显示钢筋簇”叠加查看。
- 按名称或 IFC GlobalId 搜索，上一根／下一根切换，聚焦当前对象。
- 原设计模型、计算网格（中性色）、Scan-vs-BIM 偏差着色、隐藏设计四种显示方式；计算网格和偏差使用同一份结果 PLY。
- 独立显示钢筋簇，选择可靠对应、待复核或两者合并。待复核簇没有参与本次偏差计算。空对应不借用相邻钢筋。
- “计算网格 + 钢筋簇”在有有效结果时使用本次计算 PLY；无结果时显示“原模型 + 钢筋簇”。面板同时显示当前可见网格的顶点数与三角面数。
- 青色箭头可选择当前网格保存的顶点法向，或从三角面心出发、按面片绕序计算的面法向；默认显示当前隔离钢筋的全部设计法向，可关闭“显示全部设计法向”改为抽样。橙色箭头在预览点上根据已保存的实测截面复现径向法向，继续使用采样上限。长度以毫米设置。
- 导出当前钢筋的 JSON，包括资产 ID、去噪与计算版本、映射哈希、实际计算参数、统计、截面剖面、实例目录及显示设置。
- “退出隔离”恢复所有钢筋和结果配色；切回前序步骤也会清理箭头。未完成偏差计算时仍可通过去噪目录检查设计和钢筋簇对应。

## 法向来源与限制

顶点模式中，原设计显示读取源模型顶点法向；计算网格显示读取结果 PLY 的顶点法向。面法向模式从当前可见三角面的面心出发，严格保留三角面绕序，不做方向修复；它用于区分侧面、端盖与边缘处的平滑顶点法向。两种模式均不是逐顶点搜索匹配连线，也不表示求解器已经接受该法向对应。设计法向全量显示时跳过无效或零长度法向；面板同时显示箭头数与当前顶点／三角面数。采样上限只作用于扫描箭头和显式开启抽样的设计箭头，不会改变输入网格。

扫描径向量在模型坐标系中根据 `longitudinalProfile` 的同一 `designUnitId`、`stationM`、实测中心、半径与 `windowM` 重建，然后变换到查看器坐标。缺测截面不跨越插值，越过支撑窗口或半径门限不绘制。旧结果缺少截面、实例缺少单元身份时不猜测方向。只有一条截面记录时无法从设计剖面恢复轴向，也不绘制箭头。

扫描预览点与求解器体素下采样后的点集不同；箭头用于检查截面方向与支撑范围，不能当作本次算法逐点匹配的原始输出。本次改动不调整匹配算法、阈值或保存的计算结果。

逐根结果的 `vertexStart/vertexCount` 对应合并 PLY 的顶点流，不能应用到分片局部顶点编号。查看器对逐钢筋结果使用该 PLY，过滤索引时保留顶点／偏差数组绑定。聚焦和箭头同时遵守索引及 `drawRange`，避免把预览缓冲区内隐藏点纳入隔离画面。

## 两端箭头与端盖朝向排查（2026-09-13）

“设计 + 钢筋簇”旧快捷操作总是选择 `bimPivot`（源 `model.glb`），即使已有细分后的计算结果。因此原模型中只有两圈顶点的直段只在两端显示顶点法向。现快捷操作在有结果时选择 `c2mSceneGroup` 的中性色计算网格，原模型仍可显式选择；无结果时保留检查原模型与钢筋簇的能力。

对本地模型资产 `88d5ff2f0b10c8507273a309` 的同一根钢筋 `1b9YNqdvPA1AzGxyF9pvxA`，直接读取源 GLB 与分析产物 `am-e38ab53d7057cc9df8f0d0baa8f77f24` 后得到：

| 项目 | 原始显示 GLB | 细分分析网格 |
| --- | ---: | ---: |
| 顶点数 | 106 | 1,874 |
| 三角面数 | 100 | 3,744 |
| 轴向位置数（坐标舍入至 1 μm） | 2 | 117 |
| 两端端盖面法向 | 两端均为 +轴向，一端朝内 | 分别为 −轴向、+轴向，均朝外 |

原模型该根钢筋 54 个侧面顶点法向全部朝外；52 个端盖顶点法向中，负轴端的 26 个朝内。负轴端的 24 个三角面绕序也朝内，因此不是单独的法向属性缓存问题。细分网格两端各 16 个端盖三角面均朝外；`RebarSolid` 检查为 1 个有效闭合 part、0 个无效 part、0 个翻转面。这个抽查不代表截图中未标明 IFC ID 的钢筋已被唯一识别，也不代表所有原模型构件均已逐一检查。

实际比对链路为 Go `currentAnalysisMesh` → `analysis_mesh_path` → Python `compute_instance_comparison` 按 IFC ID 读取分析瓦片，核验顶点数与位置哈希，再经 `RebarSolid` 计算可信外法向。合并 PLY 保留该顶点流及法向。此次修改不重写原 GLB、不更改求解器或已有结果；原模型的错误方向在调试中仍如实保留。

本次验证：`npm run build` 通过，18 项 Python 实体/逐筋计算测试通过；23 项前端测试及真实 Three.js 场景脚本通过，覆盖默认对照网格、无结果回退、面心法向、反向绕序、非均匀缩放与旋转、可见索引及资源释放。浏览器工具返回无可用浏览器，未执行浏览器目视验收。

## 细分网格箭头被抽稀（2026-09-13）

旧显示层默认使用 200 条上限，再按 `ceil(可见数量 / 上限)` 的步长选取顶点或三角面。读取本地真实计算 PLY、隔离 `1b9YNqdvPA1AzGxyF9pvxA` 后，1,874 个顶点仅绘制 188 条箭头，3,744 个三角面仅绘制 198 条箭头；全量模式分别可绘制 1,874 和 3,744 条。这证明该样本的箭头稀疏来自显示采样，不能据此推断 remesh 网格或求解器的法向数量不足。

逐根调试现默认全量显示设计法向，保留抽样开关，并在状态文字和导出 JSON 中记录显示模式与箭头数。扫描径向箭头仍按预览预算采样。场景回归先复现“1,783 个可见顶点仅绘制 199 条”，修改后验证顶点／面全量、显式抽样、默认设置、隔离及资源释放。此修复只涉及法向可视化，不修复偏差计算中的灰色缺测长段。

## 调试首屏加载（2026-09-13）

`debugBar` 目前在前端过滤整批结果，尚未按钢筋单独下载网格。YB-1 的合并比较 PLY 为 31,013,210 字节、402,812 个顶点；去噪预览为 10,000,224 字节、500,000 个点。旧流程即使默认隐藏扫描，也会请求并解析预览。现延迟到“显示钢筋簇”或“计算网格 + 钢筋簇”开启时加载，退出隔离恢复普通预览；已有请求仍共享同一加载 Promise。

服务器本机通过 `10.0.0.4:5174` 测量，比较 PLY 约 0.154 秒、预览约 0.101 秒；Node 使用实际 Three.js 解析器测得约 293 ms、355 ms，选中这根的全量法向构建约 8.5 ms。这些数值不包含用户设备网络、浏览器模块加载、GPU 上传或绘制，不能当作浏览器首屏耗时。保留基准脚本及结果在忽略目录 `.cloudbim/rebar-load-audit/`。默认隐藏扫描的不必要请求已由失败转通过的回归验证；24 项前端测试与场景脚本通过。

## 结果切换后的 409（2026-09-13）

后续后端访问日志确认，用户链路的两次整批 PLY 请求分别持续约 57.4 秒和 59.9 秒；本机快速下载不能排除这条实际链路的传输等待。10:21:01 新计算已保存，10:21:26 旧页面仍请求 `f492856d…` 版本的着色文件，返回 409；当前有效版本为 `2c9a6a66…`。服务端原始说明为“C2M 结果版本已变化，请刷新后重试”。

前端原先按 Blob／ArrayBuffer 下载产物，错误 JSON 也被保留为二进制，导致只显示 Axios 的英文状态码。现在响应拦截器会解码小型错误正文并保留 HTTP 状态。网格首次 409 时刷新最新结果；若为新且有效的版本，清理旧场景并同步距离、统计、显示参数后重试一次。相同版本、输入过期和第二次 409 不循环重试；已被新操作或切换资产取代的请求不覆盖当前场景。未放宽服务端版本与输入新鲜度校验。

回归覆盖真实 Axios 拦截器的 JSON／Blob／ArrayBuffer 错误、非 JSON 回退，以及场景加载的新版本恢复、相同版本、过期输入、再次冲突和并发操作取代。通过 25 项 HTTP／生命周期回归及 Three.js 场景脚本。真实旧版本 URL 的 409 和当前版本资源的 HTTP 206 已验证；没有可用浏览器，尚未执行用户页面的目视验收。
