# 分析第一步的渐进点云加载

## 原因与修复

点云本身是 3D Tiles 分块。原来的 `requestRender` 在 BIM、点云根节点及保存的配准尚未全部就绪时，把共同的 `contentGroup` 隐藏。瓦片虽然已经下载、解析，仍无法显示；BIM 就绪后，积累的点云同时出现。

`AlignmentPage.vue` 现在采用以下顺序：

1. 初始化视口后，同时启动点云、BIM、保存的配准和网格状态请求。网格状态不再阻塞几何下载，配准查询由多个完成回调共用一个在途请求。
2. 并行读取点云资产、可用表示及预处理版本。仍只选择对应版本的无台面点云，不回退为原始扫描。
3. 收到根 tileset 后，用完整边界定位相机；每个 `load-model` 只处理新到达的瓦片，立即参与渲染。BIM 等保存的姿态恢复后显示。
4. 立即启动根节点请求，下载队列不再等待下一帧；解析继续使用库的分帧队列及默认并发。首轮细化期间先直接渲染，稳定后恢复 EDL。尝试降低并发后实测细化变慢，最终没有保留该限制。
5. BIM 的构件 metadata 与 GLB 并行下载。C2M 历史及逐顶点距离仅在进入步骤 3/4 时获取；首屏保留用于判断后续步骤可用性的去噪状态。

加载状态在首个可渲染瓦片到达时解除，随后显示已载入分块数。库可能先发出 `tiles-load-end`，再完成个别 `load-model` 回调，因此状态按本轮开始/结束事件维护，避免全部结束后仍显示“细化中”。旧请求或旧瓦片回调不能覆盖新加载的状态。

## 坐标与相机约定

继续沿用 [配准坐标约定](alignment-coordinate-frames.md)：米制、右手工程坐标，公共节点通过 `Rx(-π/2)` 映射 `(x,y,z) → (x,z,-y)`；不改变源顶点、轴向或保存的扫描到 GLB 矩阵。

整体居中使用完整 tileset 边界，而非当前已经到达的部分点云。点云已定位后，若 BIM 到达或恢复配准使共同容器平移了 `Δ`，相机位置和 OrbitControls 目标同时平移 `Δ`，保持点云的屏幕投影和用户朝向。BIM 后到不再重新执行全景定位。相对配准矩阵中共同的平移仍相互抵消。

回归使用三个非对称点检查屏幕投影、相机四元数及重复居中的幂等性；原有保存/恢复矩阵和原始 RGB 回归继续保留。

## 2026-10-28 本地验证

数据为点云资产 14、BIM 资产 13。使用独立 Chrome、1600×900 视口及真实组件/资产，比较修改前组件与修改后组件，清空浏览器缓存。计时从组件挂载开始，首批指标为首个点数超过 100 的瓦片进入绘制；不包含登录或下载应用脚本的时间。

| 场景 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 本地正常响应：首批点云进入绘制 | 0.98 s | 1.09 s |
| 仅给 BIM GLB 请求增加 4 s 延迟：首批点云进入绘制 | 4.60 s | 0.43 s |
| 同一延迟场景：BIM 保存姿态恢复 | 4.57 s | 4.75 s |

正常本地响应下没有观察到稳定的首屏提速，不能把延迟对照解释为所有网络条件下的加速比例。对照证实：旧版点云在约 1.35 s 已完成加载但被隐藏；新版在 BIM 尚未返回时已显示点云，并持续增加细节。保留了该阶段与最终场景截图。修改前后从真实浏览器场景重建的扫描到 GLB 相对矩阵最大元素差为 **0**，最终瓦片失败数为 **0**。

正常首步网络记录中，移出的 C2M JSON 和距离数据分别为 1,901,155 与 1,623,504 字节，合计 3,524,659 字节。实际主应用切到步骤 3 后仍能获取并显示已有偏差结果；验证没有重新执行配准、去噪或偏差计算。

本机过程证据在忽略目录 `.cloudbim/analysis-loading-20261028/`：`timings.json`、`delayed-bim.json`、`after-delayed-bim-progress.png`、`after-delayed-bim.png`。其中标记为 `invalid-*` 的早期记录因对照样式缺失作废，不用于结论。常规 DevTools 浏览器曾被限制在约 1 FPS，该会话的绝对时间也不用于性能结论。
